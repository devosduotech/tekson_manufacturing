## Overview

v15.1.40 replaces the "first workstation of the type, alphabetically" Job Card
assignment with a shared, scheduling-agnostic selection service that rotates
across the eligible machines of the **Workstation Type** configured on the BOM
Operation.

No doctype, field or permission JSON changes: this release is Python-only.
Deployment is `git pull` + `bench restart`; `bench migrate` and
`bench build` are not required.

**Deployment gate:** capacity planning must remain disabled
(`Manufacturing Settings → Disable Capacity Planning` ticked). ERPNext assigns
the first workstation of the type while scheduling, *before* the Job Card
`before_insert` hook runs, and that pick is intentionally respected. Verify
with the diagnostic in section "Deployment checks" below.

## What's Included

### Workstation Type routing (`utils/job_card_utils.py`)

- **Type is the routing key.** `BOM Operation.workstation_type` is resolved to
  a group of interchangeable machines; the hook then rotates within that group.
  If the BOM Operation cannot be resolved, the `workstation_type` ERPNext copied
  onto the Job Card from the Work Order Operation is used instead.
- **`pick_workstation()` is the shared selection service.** It exposes a
  `candidates` argument for the future capacity planner to pass slot-eligible
  machines. Rotation is then a tie-breaker inside that subset.
- **Selection order:** machines not at their concurrent capacity
  (`active_load < production_capacity`) → least recently used → fewest queued
  Job Cards (`open_load`) → workstation name.
- **`last_used` is actual production activity**, not Job Card creation:
  `actual_end_date`, or "now" while a Job Card is running. Queued Job Cards that
  never started do not count; cancelled Job Cards are ignored; a machine that
  has never run work sorts first.
- **Excluded machines:** `Maintenance` and `Problem` only. `Off` and `Idle`
  remain eligible because ERPNext sets a workstation to `Off` when a Job Card
  on it completes.
- **Never rotated:** a workstation already present on the Job Card (user or
  capacity-planner choice) is left untouched. There is no post-scheduling
  override of `scheduled_time_logs`.
- **Legacy machine-in-BOM rows** are treated as a preference: honoured when
  eligible, otherwise rotation falls back to the machine's type and logs the
  blocked machine. Teksons routes by type, so this path only covers old data.
- **Job Card save is scoped to its operation.** The validate hook called the
  material engine without the Job Card, so a save replaced the per-operation
  shortage list with the whole Work Order's list while the readiness refresh
  used the per-operation result. Both paths now pass the Job Card. This was
  exposed by the diagnostics section 6 consistency check on the Test Server.
- **All machines at capacity:** the least recently used machine is still
  assigned so Work Order submission is never blocked, and a warning is logged.

### Diagnostics (`scripts/diagnose_mes_performance.py`)

New read-only section 7 "Workstation routing":

- capacity-planning setting **and** recent Job Cards that actually carry
  scheduled time logs (proves whether the real Work Order flow scheduled)
- BOM Operations without a Workstation Type
- Workstation Types with no usable workstation
- Workstation Types spanning multiple plant floors (WIP-warehouse mapping risk)
- workstations running more concurrent Job Cards than `production_capacity`
- Workstation Types with two or more eligible machines, i.e. where rotation can
  actually be observed
- the machines used by Job Cards created in the last 24 hours, grouped by type;
  all cards on one machine is flagged as a rotation failure

Also adds `("tabJob Card", ["workstation", "docstatus"])` to the index
candidates for DBA review (not created automatically).

Sections 1 and 2 now read their field names from doctype metadata, fixing
`Unknown column 'doc_type'` and `Unknown column 'title'` on current Frappe v15
(`Server Script.reference_doctype` / `doctype_event`, `Error Log.method`).

## Deployment checks

```bash
git pull
bench --site <site> restart
bench --site <site> execute tekson_manufacturing.scripts.diagnose_mes_performance.run
```

Expected in section 7:

- `Capacity planning disabled — Job Card rotation is authoritative`
- `no Job Card from the last 30 days carries scheduled time logs`
- `every active BOM Operation has a Workstation Type`
- `every Workstation Type has at least one usable workstation`
- no workstation above `production_capacity`

Then submit a representative Work Order and confirm its Job Cards rotate across
the eligible machines of each operation's Workstation Type.

## Verification

- Offline stub suites for `pick_workstation()` and `allocate_workstation()`:
  true-LRU rotation, queued-vs-active semantics, concurrent capacity,
  `candidates` filtering, blocked statuses, all-at-capacity fallback,
  cancelled-Card exclusion, type-first routing vs legacy machine rows,
  pre-assigned preservation, and blocked-machine fallback.
- `python3 -m py_compile` and `ruff check` clean on the changed files.

Transaction safety (two simultaneous Job Cards reading the same workload
snapshot) is not covered by the offline tests; confirm on the Test Server with
concurrent Job Card creation.
