## 1. Problem

Every Job Card for a Workstation Type was allocated to the first machine
returned by ERPNext's `get_workstations(type)` (`[0]`). Siblings stayed idle
while one machine became the bottleneck. The BOM never names a specific
machine, only a Workstation Type.

## 2. What changed

### 2.1 Type-first workstation routing

`tekson_manufacturing/utils/job_card_utils.py`

- `pick_workstation(workstation_type, reasons=None, candidates=None)` is the
  single selection service. `candidates` is the seam for a future capacity
  planner (planner passes slot-eligible machines; rotation orders that subset).
- `allocate_workstation(doc, method=None)` runs on Job Card `before_insert` and
  never replaces a workstation that is already set (user or planner choice).
  `scheduled_time_logs` are never touched.
- Routing key resolution order:
  1. BOM Operation `workstation_type`
  2. `workstation_type` copied onto the Job Card from the Work Order Operation
  3. legacy explicit machine on the BOM Operation — treated as a **preference**:
     honoured when eligible, otherwise fall back to that machine's type and log
     the blocked machine

### 2.2 Workload model

| Metric | Meaning | Used for |
|---|---|---|
| `active_load` | Job Cards in `Work In Progress` / `On Hold` (`docstatus < 2`) | compared with `Workstation.production_capacity` |
| `open_load` | Job Cards not `Completed` / `Cancelled` (`docstatus < 2`) | queue balancing; **not** a hard availability filter |
| `last_used` | latest `actual_end_date`, or `NOW()` for a running Job Card; cancelled and never-started cards do not count; never-used machines sort first | rotation tie-break |

Selection ordering (best first):

1. machines not at concurrent capacity (`active_load < production_capacity`)
2. fewest queued Job Cards (`open_load`)
3. least recently used (`last_used`)
4. workstation name (stable tie-break)

`open_load` is ordered before `last_used` because queued Job Cards never update
`last_used`; without this a batch of new Job Cards all compared equal and landed
on the same machine.

### 2.3 Eligibility

- Blocked: `Maintenance`, `Problem`, `Setup`
- Eligible: `Off`, `Idle`, `Production`
  - ERPNext sets `Off` automatically when a Job Card completes, so `Off` cannot
    mean "unavailable"
  - a queued Job Card is not started immediately, so transient operational
    states should not remove a machine from allocation
- If every machine of a type is blocked, no assignment is made and the reason
  is logged (`no eligible Workstation of type '...'`).
- If every machine is at capacity, the least loaded machine is still assigned so
  Work Order submission is never blocked, with a warning; the diagnostic reports
  the overflow.

### 2.4 Job Card readiness scope fix

`tekson_manufacturing/services/job_card_service.py`

The validate hook called `MaterialReadinessEngine.evaluate_material_readiness()`
without the Job Card, so saving a Job Card replaced the per-operation shortage
list with the whole Work Order's list. The readiness refresh already used the
per-operation evaluation. Both paths now pass `job_card`, so save and refresh
agree. Surfaced by the diagnostic consistency section.

> This was not part of the original workstation requirement, but it was found
> during validation and would have produced misleading material details on
> every Job Card save.

### 2.5 Diagnostics

`tekson_manufacturing/scripts/diagnose_mes_performance.py` (read-only)

- Sections 1/2 use current Frappe v15 field names
  (`Server Script.reference_doctype` / `doctype_event`, `Error Log.method`);
  section 2 reports 24h counts and latest timestamp per title so a historical
  backlog is not mistaken for ongoing logging.
- Section 7 "Workstation routing":
  - capacity-planning setting, plus proof of whether scheduling actually ran
    (recent Job Cards carrying scheduled time logs)
  - BOM Operations without a Workstation Type
  - Workstation Types with no usable machine
  - types that can rotate (2+ eligible machines)
  - machines excluded by `Maintenance` / `Problem` / `Setup`, with status
  - assignments of Job Cards created in the last N hours, grouped by type;
    all cards on one machine is flagged as a rotation failure
  - workstations above `production_capacity` (active / capacity / queued)
- Adds `("tabJob Card", ["workstation", "docstatus"])` to the index candidates
  for DBA review (no index is created by the app).

## 5. Known limitations / accepted behaviour

1. **No scheduling.** Allocation is a creation-time decision; capacity is soft.
   Two simultaneous Job Cards can land on the same machine. This is accepted
   and reported separately as capacity overflow.
2. **Not retroactive.** Existing Job Cards keep their assigned machine.
3. **Capacity planning must stay disabled** (`Manufacturing Settings → Disable
   Capacity Planning`). ERPNext schedules before the `before_insert` hook and
   its choice is respected. The diagnostic verifies this in the real flow.
4. **`last_used` does not model setup duration**, only actual start/end.
5. **Queued work can diverge from physical load**: `open_load` balances planned
   cards, not machine time.
6. **Index candidates are not created.** Missing composite indexes remain a DBA
   decision.
7. **Error Log backlog** (pre-v15.1.32) and the volume of `Security Event:`
   audit entries are recorded as findings, not changed in this release.
